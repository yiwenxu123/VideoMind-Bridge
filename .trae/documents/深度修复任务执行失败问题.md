## 问题分析

从日志分析，问题有以下几个层面：

### 1. HTTP 416 错误（根本原因）
- 这是 yt_dlp 的网络下载错误
- 可能是视频源服务器不支持断点续传
- 或者是网络连接问题

### 2. 异常处理混乱（加剧问题）
- 当 yt_dlp 遇到 HTTP 416 错误时，正在处理异常
- 但我们的回调函数可能又抛出了 InterruptedError
- 导致 "During handling of the above exception, another exception occurred"

### 3. 取消机制问题
- 在回调中抛出 InterruptedError 会中断 yt_dlp 的正常流程
- 可能导致资源未正确释放

## 修复方案

### 方案：安全取消机制

**核心思想**：不在回调中抛出异常，而是使用标志位让下载自然完成后再检查取消状态。

**1. 修改 ProcessingWorker**
- 添加 `_should_stop` 标志位
- 回调只更新标志位，不抛出异常
- 下载完成后检查标志位

**2. 修改 download_service**
- 支持外部取消检查
- 或者使用更安全的取消方式

**3. 修改异常处理**
- 区分网络错误和取消操作
- 网络错误显示为失败
- 取消操作显示为已取消

### 具体实现

**processing_worker.py:**
```python
def __init__(self, ...):
    ...
    self._should_stop = False

def cancel(self):
    self._should_stop = True
    self.requestInterruption()

def _check_should_stop(self):
    return self._should_stop or self.isInterruptionRequested()

def download_progress(status, percent):
    if self._check_should_stop():
        self._should_stop = True  # 设置标志位
        return  # 不抛出异常
    self.progress_updated.emit(...)

# 下载完成后检查
result = self.download_service.download(...)
if self._should_stop:
    raise InterruptedError("任务已取消")
```

### 备选方案

如果上述方案仍然无法解决 HTTP 416 错误，可能需要：
1. 更新 yt_dlp 到最新版本
2. 更换视频源
3. 添加重试机制（在 download_service 层面）

## 预期效果
- 取消操作不会导致 yt_dlp 内部异常
- 网络错误和取消操作正确区分
- 系统更加稳定
